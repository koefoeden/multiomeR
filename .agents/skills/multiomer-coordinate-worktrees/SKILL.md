# Coordinate multiomeR Worktrees

Create top-level Codex App tasks that the user can track individually. Do not
use collaboration subagents, fork the coordinator task, or create Git
worktrees manually for this workflow.

Accept a numbered `Tasks:` list plus shared or task-specific constraints. If no
concrete tasks are supplied, request the task list before dispatching.

## Dispatch workers

1. Identify task dependencies. Dispatch only independent tasks in parallel.
2. Resolve the requested App project and verify its live checkout path; do not
   rely on a remembered project ID.
3. Create one user-owned App task per item with environment type `worktree`.
   Do not assume an autogenerated Codex environment configured the worktree.
4. Omit `startingState` unless the user names an existing branch or requests
   the current working tree.
5. Give each task a short unique title and plan a unique `codex/<task-slug>`
   branch. Check for existing branches before choosing the name.
6. Start independent task-creation calls concurrently.

Put the complete scope, constraints, and validation requirements in each
worker's initial prompt. Require every worker to:

- read applicable `AGENTS.md` files;
- use the global `$r-manage-targets-worktrees` skill;
- inspect its actual worktree and lifecycle state before editing;
- choose and configure the least-permissive sufficient setup itself;
- default to read-only and convert only when target execution is required;
- use the smallest complete endpoint set for selective conversion;
- stop on partial, conflicting, or unknown runtime state;
- leave the base checkout, target store, unrelated files, and other worktrees
  untouched;
- report progress and blockers in its own task.

Do not embed repository-local setup scripts in worker prompts. The shared
runtime and its global skill are the canonical lifecycle contract.

## Perform and report the task

After setup, require the worker to:

1. create and switch to its planned branch;
2. confirm its worktree, branch, and targets-worktree state;
3. make only the requested changes;
4. validate proportionally to risk;
5. report its branch, changed files, validation, lifecycle state, and any
   blocker.

Do not commit, push, open a pull request, merge, promote output, or tear down a
worktree unless the user explicitly requests that action. When teardown is
authorized, require the worker to use the shared runtime before Git removes
the worktree. Writable stores are quarantined, not deleted.

## Return trackable tasks

Wait for provisioning to produce permanent task IDs, then return each title,
task ID, planned branch, lifecycle state, and current status. Emit one task
directive per successfully created task:

```text
::created-thread{threadId="<permanent-task-id>"}
```

Do not claim readiness before a permanent ID exists. Report provisioning
failures separately with their client task IDs.

## Monitor and hand off

- Summarize task link, App status, branch, lifecycle state, latest milestone,
  blocker, and next action without interrupting workers.
- Send follow-up prompts only when the user requests more work.
- Use App handoff only on worker task IDs, never on the coordinator task.
- Hand workers back to a base checkout one at a time.

Keep the coordinator in the base checkout and free of worker edits.
