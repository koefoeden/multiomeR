5  Main pipeline

5.1 Purpose

This workflow is defined in _targets.R and represents the main analysis pipeline after Cell Ranger output generation. It processes individual 10x reactions in parallel, combines selected reactions into aggregations, and builds RNA/ATAC outputs for clustering, cell typing, WNN integration, subgroup reprocessing, and optional downstream modules.

Representative outputs from the public example workflow are collected in the Output Gallery.

5.2 Inputs

The main pipeline is configured in three layers: datasets define shared genome and QC settings, reactions point to individual 10x outputs, and aggregations choose which reactions to process together.

Each YAML file has a default entry with shared parameters. Named datasets and aggregations inherit from default unless they declare another inherits parent, so template entries usually only list required values and settings that intentionally differ from the defaults.

5.2.1 cfg_datasets.yaml

Dataset-level settings live in cfg_datasets.yaml. A dataset is the shared context for one or more 10x reactions, typically a genome/reference combination plus dataset-wide QC rules. Reactions in cfg_reactions.tsv refer to these dataset keys, so define datasets before adding reaction rows.

Typical dataset-level settings include:

  • dataset_cellranger_arc_refdata_dir: Cell Ranger ARC reference directory for the dataset genome.
  • dataset_QC_exclude_list_per_reaction: reaction-level QC filters applied before aggregation.

The public PBMC example uses the following dataset entry, rendered directly from cfg_datasets.yaml:

Show immune_human_dataset 
immune_human_dataset:
  mandatory:
    dataset_cellranger_arc_refdata_dir: example_data/refdata-cellranger-arc-GRCh38-2020-A-2.0.0
  optional:
    dataset_QC_exclude_list_per_reaction:
      - TSS.enrichment < 4
      - nucleosome_signal > 4
      - nCount_RNA < 250
      - RNA_mito_percent > 10
      - amulet_q.value < 0.05

5.2.2 cfg_reactions.tsv

Reaction-level configuration lives in cfg_reactions.tsv. Add one row per 10x reaction with a stable reaction_ID, the matching dataset, the reaction_cellranger_count_dir, and any donor demultiplexing fields relevant to that reaction.

The reaction table columns are:

Column Meaning
reaction_ID Stable reaction identifier used throughout target names and downstream config.
dataset Dataset key used to join dataset-level settings from cfg_datasets.yaml.
reaction_donor_id Donor ID assigned to all nuclei in a non-multiplexed reaction. Use NA for multiplexed reactions.
reaction_n_donors Number of donors expected in the reaction.
reaction_cellranger_count_dir Path to the cellranger-arc count output directory.
reaction_cellbender_h5_file Optional CellBender-corrected GEX H5 file. Use NA when not used.
reaction_donors_VCF_file Optional VCF for donor demultiplexing. Use NA when not used.

5.2.3 cfg_aggregations.yaml

Aggregation-level settings live in cfg_aggregations.yaml. An aggregation combines one or more configured reactions and controls merged RNA/ATAC processing, clustering, annotation, plotting, and optional downstream modules.

At minimum, each aggregation needs:

Field Meaning
aggregation_reaction_IDs Reaction IDs from cfg_reactions.tsv to include in the joint analysis.
aggregation_GEX_marker_genes Named marker-gene lists used for module scoring and cluster annotation.
aggregation_donor_id_metadata_tsv Donor-level metadata table with a donor_id column.
aggregation_reaction_ID_metadata_tsv Reaction-level metadata table with a TENX_reaction_ID column.

Optional aggregation settings control QC filters, RNA and ATAC dimensions, clustering resolution, UMAP parameters, subgroup analysis, plotting variables, track export, and enabled modules. YAML entries are divided into mandatory parameters that must be set and optional parameters that are usually inherited from default unless the entry overrides them. NULL values intentionally disable optional behavior.

Each aggregation also points to metadata files:

  • aggregation_donor_id_metadata_tsv: donor-level metadata with a donor_id column matching the donor IDs assigned during per-reaction processing.
  • aggregation_reaction_ID_metadata_tsv: reaction-level metadata with a TENX_reaction_ID column matching the configured reaction IDs.

These metadata tables are joined to the per-cell metadata before downstream correction, plotting, and modelling.

The public PBMC aggregation below is rendered directly from cfg_aggregations.yaml. It shows the required aggregation inputs plus the example-specific optional overrides; standard optional settings are inherited from default.

5.3 Running the pipeline

From the repository-root R session described in Installation, run the main workflow in checkpoint-sized pieces. Replace your_aggregation with the aggregation name from cfg_aggregations.yaml, for example blood_human.

5.3.1 GEX checkpoint

Run the RNA-processing checkpoint first:

targets::tar_make(
  names = targets::tar_described_as(tidyselect::contains("checkpoint:GEX")) &
    tidyselect::matches("your_aggregation")
)

At this checkpoint, inspect the aggregation-level barcode exclusion summaries, RNA-only QC plots, marker summaries, and GEX_Seurat_object.your_aggregation. If the GEX filtering, clustering, and annotation look acceptable, continue to the ATAC checkpoint.

5.3.2 ATAC checkpoint

Run the ATAC-processing checkpoint after the GEX review:

targets::tar_make(
  names = targets::tar_described_as(tidyselect::contains("checkpoint:ATAC")) &
    tidyselect::matches("your_aggregation")
)

At this checkpoint, inspect ATAC QC plots, LSI diagnostics, peak and motif summaries, coverage tracks, and TF or gene activity plots. If the ATAC processing looks acceptable, continue to the multimodal checkpoint.

5.3.3 Multimodal checkpoint

targets::tar_make(
  names = targets::tar_described_as(tidyselect::contains("checkpoint:multimodal")) &
    tidyselect::matches("your_aggregation")
)

At this checkpoint, inspect WNN UMAPs, modality-weight plots, multimodal cluster comparisons, and multimodal_Seurat_object.your_aggregation. Optional downstream modules are described in their own walkthroughs.

To run all configured aggregations for a checkpoint, omit the & tidyselect::matches("your_aggregation") part. To run the full workflow after checkpoint review, run:

targets::tar_make()

The full main pipeline can be computationally expensive. Start with the public example or a narrow target selection, then scale to larger datasets after local paths, metadata files, and controller settings are working.

The workflow output directory can be changed with the store field in _targets.yaml.

5.4 Implementation details

The diagrams below are meant to make the pipeline easier to reason about before reading the target code directly. They are generated from tagged target metadata and the real {targets} dependency graph, then simplified by pruning or bypassing lower-level nodes that would make the view harder to read. They keep real target names and preserve the dependency structure where practical, while staying compact enough to build intuition about the main control points.
